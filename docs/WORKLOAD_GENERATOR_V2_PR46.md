# PR46 — Workload Generator v2

## Purpose

PR46 replaces ad hoc publication-trace construction with one versioned, deterministic workload generator for the ADES publication campaign.

**Claims directly addressed:** `C2`, `C8`.

It also supplies controlled workload axes later used to evaluate `C4`–`C7` and mechanism hypothesis `C9`. PR46 establishes generator semantics and reproducibility; it does not establish a performance claim.

## Reproducibility identity

A generated workload is identified by the tuple:

```text
exact graph file bytes
seed
canonical WorkloadConfig v2
```

The generator records:

```text
graph_sha256
seed
config_sha256
trace_sha256
query_count
update_count
increase_count
decrease_count
complete generator config
```

`graph_sha256` hashes the exact graph file bytes supplied to the generator. For committed DIMACS `.gr.gz` inputs, this therefore identifies the compressed corpus file, not a reserialized graph.

`trace_sha256` hashes the canonical PR42 operation grammar. `ades_workload_v2` writes that canonical stream, reloads it, validates every recorded `old_weight` against the evolving graph, and requires the persisted file SHA-256 to equal the in-memory canonical trace SHA-256.

The same graph bytes + seed + config must produce byte-identical trace output. The CLI metadata is deliberately timestamp-free and path-independent so repeated invocations with the same scientific inputs are also byte-identical.

## Deterministic random engine

Workload Generator v2 uses `std::mt19937_64` seeded directly from the declared 64-bit seed. It does not use `std::shuffle`, `std::uniform_*_distribution`, or implementation-defined floating random distributions.

Selection is implemented using explicit engine draws and integer arithmetic. The hot-source permutation uses a deterministic Fisher-Yates prefix construction. Zipf-like source sampling uses fixed integer rank weights `1,000,000 / rank`.

This choice minimizes library-dependent variation in generated bytes.

## Frozen source families

The generator supports exactly these publication families:

### `uniform`
Every source is selected uniformly from all vertices. `locality_percent` is recorded but does not alter this family.

### `single-hot`
With probability `locality_percent / 100`, use one fixed hot source. Otherwise use a uniform source.

### `hot-pool`
With the locality probability, choose uniformly from the deterministic hot-source pool. Otherwise use a uniform source.

### `zipf`
With the locality probability, choose from the deterministic hot-source pool using integer rank weights proportional to `1/rank`. Otherwise use a uniform source.

### `rotating-hot`
With the locality probability, use one active hot source for `epoch_queries`, then rotate to the next source in the hot pool. Otherwise use a uniform source.

### `churn`
With the locality probability, rotate to the next hot source every query. Otherwise use a uniform source.

This makes `rotating-hot` a phase-persistent hotspot process and `churn` a deliberately high-turnover source process.

## Locality parameter

```text
locality_percent ∈ [0, 100]
```

For non-uniform families, this is the exact probability of selecting through the family-localized branch rather than the global uniform fallback.

It replaces the previously hard-coded 90%/95% locality constants in exploratory generators with an explicit scientific parameter.

## Frozen update rates

`update_interval` is restricted to:

```text
0, 2, 5, 10, 50, 100
```

Interpretation:

- `0` — static/no-update control;
- `2` — one scheduled update per two queries;
- `5` — one per five queries;
- `10` — one per ten queries;
- `50` — one per fifty queries;
- `100` — one per one hundred queries.

For non-bursty modes, an update is emitted before query indices `interval, 2*interval, ...` using zero-based query numbering. Thus the exact planned update count is:

```text
floor((query_count - 1) / update_interval)
```

for nonzero intervals.

## Frozen update modes

### `increase-only`
Every scheduled update strictly increases an edge weight.

### `decrease-only`
Every scheduled update strictly decreases an edge weight.

### `balanced-random`
Each update direction is selected from a seeded random bit. The exact realized increase/decrease composition is recorded in metadata.

### `strict-alternating`
Directions alternate deterministically, beginning with an increase.

### `bursty`
The total update count remains exactly the count implied by `update_interval`, but updates are temporally clustered into groups of `burst_length`. Direction alternates globally, beginning with an increase.

This changes temporal clustering without silently changing the total update load.

### `repeated-edge`
One deterministic edge and one deterministic perturbation delta are selected at the first update. The generator then toggles that same edge between its anchor weight and `anchor + delta`, beginning with an increase.

This creates a repeated-edge stressor without cumulative weight drift.

## Frozen perturbation magnitudes

Magnitude bands are absolute integer edge-weight changes:

```text
small   = [1, 3]
medium  = [4, 31]
large   = [32, 255]
```

For a requested direction, the generator selects an edge capable of supporting at least the lower bound, then samples a delta within the requested band and the edge's safe capacity. Decreases never underflow and increases never overflow `Weight`.

If the graph cannot support the requested update semantics/magnitude, generation fails rather than silently weakening the requested workload.

## Canonical config identity

`canonical_workload_config()` serializes the complete scientific configuration in a fixed newline-delimited order:

```text
workload_generator_version
query_count
update_interval
source_family
hot_sources
epoch_queries
locality_percent
update_mode
magnitude
burst_length
```

`config_sha256` is SHA-256 over those exact canonical config bytes. Seed and graph identity remain separate fields, allowing the same config to be reused across graphs and independent seeds without changing its config hash.

## CLI

```text
ades_workload_v2 \
  GRAPH TRACE_OUT METADATA_OUT SEED QUERIES \
  SOURCE_FAMILY UPDATE_INTERVAL UPDATE_MODE MAGNITUDE \
  HOT_SOURCES EPOCH_QUERIES LOCALITY_PERCENT [BURST_LENGTH]
```

The trace is PR42-canonical and can be consumed by replay-capable benchmark paths.

The JSON metadata schema is:

```text
ades-workload-v2
```

and contains no wall-clock timestamp or machine-specific absolute graph path.

## Acceptance tests

`ades_workload_v2_tests` verifies:

- the generic SHA-256 implementation against the standard `abc` vector;
- file-byte SHA identity;
- same seed + graph + config gives byte-identical operation streams;
- different seeds change the generated stream;
- all six source families execute;
- localized families remain within the configured hot pool when locality is 100%;
- all six update modes execute;
- static mode emits no updates;
- increase-only/decrease-only direction invariants;
- strict alternating, bursty, and repeated-edge direction balance;
- bursty mode actually contains adjacent updates;
- repeated-edge mode updates one edge only and toggles direction;
- small/medium/large delta bands;
- rejection of unsupported update intervals and invalid configuration values.

## CI gate

`.github/workflows/workload-v2.yml` performs a real-NY acceptance run and requires:

1. the committed NY graph corpus verifies;
2. the repository builds and the complete CTest suite passes;
3. two independent invocations with identical scientific inputs produce byte-identical trace and metadata files;
4. the trace SHA in metadata equals the SHA-256 of the persisted canonical trace file;
5. the graph SHA in metadata equals SHA-256 of the exact committed graph file;
6. all frozen source families, update modes, magnitude bands, and update-rate settings are exercised at least once;
7. generated artifacts are uploaded for inspection.

## Evidence interpretation

Generator determinism is a reproducibility property, not evidence that a workload is representative of every real application.

The later campaign must preserve negative and refuting workload results. The purpose of the expanded workload space is specifically to expose crossover regimes and possible fixed-strategy dominance, not to search only for ADES-favorable cells.
